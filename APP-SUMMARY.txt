--------------------------------------------------------------------------------
1. WHAT THE APP IS
--------------------------------------------------------------------------------
Audi0z: a local-only desktop music player/library (Electron 43 + React 18 +
TypeScript, built with electron-vite). It manages a single library folder on
disk (~/Music/my-music-library by default — the folder keeps the pre-rename
name so existing libraries survive — overridable via the MML_LIBRARY_DIR
environment variable), imports audio from local files or URL downloads
(yt-dlp), optionally transcodes imports to Opus 96k (ffmpeg) — at import time
or later, per file, from the Settings storage manager, and only committed when
the re-encode actually comes out smaller (otherwise the original is kept
untouched) — organises songs with a first-class tag registry, sorts any view
by date added or duration (each row shows its added date), keeps playlists in
a user-arranged order (drag to reorder; the sidebar marks the playlist the
playing queue came from), and plays audio through a custom media:// protocol
with full seek support (arrow keys skip ±10s; scrubbing is silent until
released). There is no network service, no account, and no
database — four atomically-written JSON files and a folder of audio files are
the entire persistent state.

--------------------------------------------------------------------------------
2. PROCESS ARCHITECTURE (the three Electron worlds)
--------------------------------------------------------------------------------
MAIN PROCESS (src/main/) — owns the filesystem, the stores, the media protocol,
  the ingest pipeline (yt-dlp/ffmpeg child processes), and all IPC handlers.
  Composition happens once in src/main/index.ts.

PRELOAD (src/preload/) — the only bridge. Exposes a typed `window.api` object
  to the renderer via contextBridge. The renderer never touches Node, Electron,
  or the filesystem directly (contextIsolation on, nodeIntegration off, CSP
  restricts everything to 'self' + media:).

RENDERER (src/renderer/) — the React UI. One reducer-driven state tree, a pure
  playback engine, and an <audio> element fed by media:// URLs. All server-ish
  work goes through window.api (IPC invoke) and two push channels (download
  progress, error events).

Shared contracts between all three live in src/shared/ and are the spine of
the app: every boundary speaks these types and channel names.

--- src/main/media/ — the streaming protocol ---

mediaProtocol.ts (+test) Handles media://audio/<id>: resolves the id through
                        the SHARED libraryStore, path-traversal-guards the
                        resolved file (single reusable check), implements RFC
                        9110 Range semantics (206 + Content-Range, suffix and
                        open-ended ranges, 416 past EOF), and destroys the
                        read stream on request abort so scrubbing can't leak
                        file descriptors. This is what makes <audio> seeking
                        real. v2.1: an optional awaitCompression dep is
                        awaited BEFORE the record lookup, so a request racing
                        an in-flight compression waits for the swap and
                        streams the settled file instead of erroring
                        mid-stream. v3: the dep answers undefined when
                        nothing is in flight and the handler skips the await
                        entirely — the idle path costs not even a microtask.
mimeTypes.ts (+ test)   Extension → Content-Type map with octet-stream
                        fallback. v3 added .aac (raw ADTS decodes in
                        Chromium, but only if it isn't served as
                        octet-stream); .aiff/.wma stay absent — the picker
                        accepts them but Chromium can't play them, which is
                        why the add dialog's hint no longer lists them.

registerLibraryIpc.ts   The library/playlist/tags/settings handlers. Every
(+ test)                handler validates its payload at the trust boundary.
                        v2 additions: tags CRUD (rename/remove cascade through
                        libraryStore after the registry write), library:compress
                        (delegates to the injected compressSong; v3 — answers
                        CompressResult, converting the Song to a DTO and
                        passing shrank through), and
                        library:showFolder (reveals the audio dir — the old
                        per-row Reveal's replacement). v2.1 adds

                        exists true), and the update patch accepts durationSec.

registerIngestIpc.ts    The 5 ingest handlers: probe (title lookup), start
(+ test)                (download), cancel, updateYtDlp (downloads latest into

                        extension would otherwise break ffmpeg's container
                        detection). v3 dropped the target from 128k: the
                        downloader's own sources are ~128k AAC, so a 128k
                        re-encode had no headroom and could grow the file;

                        worst-case source).
importer.ts (+ test)    importFile: the single write path into the library for
                        BOTH local adds and downloads. Generates the uuid,
                        derives the audio filename from it, copies (or
                        transcodes) into audio/, records the song in the SAME
                        libraryStore instance, cleans up on failure. v3: a
                        compress request stages the re-encode beside the
                        final name, compares sizes, and falls back to a plain
                        copy (compressed:false) when the Opus came out no
                        smaller — the rollback removes staged AND target,
                        whichever exists.
compressExisting.ts     v2, reworked in v3: compresses a song ALREADY in the
(+ test)                library — resolves the source through the same
                        path-traversal guard as the media protocol, then
                        stage-compare-commits: transcodes to
                        <id>.opus.staged, stats both files, and when the
                        re-encode is NOT smaller removes the staged file and
                        returns {song, shrank:false} with the row and the
                        original untouched (previously the smaller original
                        was deleted unconditionally and the row stamped
                        compressed forever). A win renames staged into
                        place, repoints the row via replaceFile, then
                        best-effort deletes the old file — staging beside
                        the final name is what keeps src === dst (an
                        uncompressed .opus named after its id) safe. A
                        transcode failure leaves record and directory
                        untouched.
compressionJobs.ts      v2.1: the main process's memory of which songs are
(+ test)                mid-compression — run() tracks a job under its song
                        id (settle-safe, identity-guarded cleanup so a job
                        only ever clears its own slot); waitFor() (v3)
                        answers the in-flight promise, or undefined when the
                        song has none — so an idle library pays nothing.
                        index.ts wraps compressSong in it and hands waitFor
                        to the media protocol AND (v3.1) to the library IPC,
                        so DTO measurement gets the same courtesy as
                        streaming; success and failure look the same to a
                        waiter (a failed transcode leaves the original file
                        in place).
downloader.ts (+ test)  createDownloader: orchestrates probe → download →
                        importFile with a single-flight BUSY latch (one
                        download at a time; a second start throws), an
                        AbortController per job (cancel kills the child and
                        cleans the temp job dir), and an onProgress
                        subscription seam whose listeners must not throw
                        (guarded). Custom error names (BUSY/Cancelled) do NOT
                        survive IPC serialization — the renderer matches
                        message text instead (see renderer lib/errors.ts).

--- src/renderer/src/playback/ — the pure engine ---

types.ts                PlaybackState (queueId, order, currentId, isPlaying,
                        playToken, shuffle, repeat, played, history) and the
                        action union. v3.3: playedByQueue (a per-queue map)

engine.ts (+ test)      A pure reducer — no side effects, fully unit-tested
                        (100% branch): queue selection (with an optional

                        the row-click and TopNav-play contract; without it the

                        previous (a real history stack — returns to what

                        per-queue), and (v2.1, reshaped v3.3)

4. THE KEY DATA FLOWS
--------------------------------------------------------------------------------
LOCAL IMPORT   picker → AddSongDialog → api.library.add(AddSongRequest)
               → LIBRARY_ADD handler → importFile → (optional ffmpeg
               transcode) → copy into audio/<uuid><ext> → libraryStore.add
               → SongDto back to the renderer → list refresh.

URL DOWNLOAD   AddSongDialog URL step → api.download.probe (title) → start →
               downloader (BUSY latch) → yt-dlp child (spawnLines) → progress
               lines → onProgress seam → DOWNLOAD_PROGRESS channel → dialog
               progress bar → downloaded file → importFile (same path as
               local import) → row appears. Cancel → AbortController →
               SIGTERM/SIGKILL → temp job dir cleaned → latch released.

PLAYBACK       row click → song/selected (same queue) or queue/selected +
               startSongId (playing from a view that is not the queue —
               sidebar clicks alone NEVER move the queue or pause anything)
               → engine sets currentId + bumps playToken → useAudioElement
               sets audio.src = media://audio/<id> → mediaProtocol streams
               the file (Range requests as the user seeks — v3: arrow keys
               skip ±10s and pointer drags on the slider run silent until
               release, both through the AudioController, never the store)
               → 'ended' → song/ended → engine picks next (shuffle/repeat/
               played rules) → repeat. v3: a sort change re-sorts the queue
               in place around the playing song (queue/orderChanged — no
               restart, no playToken bump).

TAG CASCADE    TagsDialog rename/delete → tags:rename/remove → tagStore
               (registry write) → libraryStore.renameTag/removeTag (every
               song, one persist) → dialog refetches tags + library → chips
               and rows update everywhere at once.

COMPRESS LATER Settings row "Compress" → library:compress → compressExisting
               (transcode to <id>.opus.staged, compare sizes; a win renames
               into place + replaceFile + delete old, a loss removes the
               staged file and keeps everything) → CompressResult back →
               library/songUpdated + a toast that tells the truth either
               way: shrank → row shows the new size and the Compress button
               disappears; not smaller → original kept, row unchanged and
               re-attemptable. Guarded off for the song currently loaded in
               the player; v2.1 covers the other direction — playing a song
               mid-compression waits (compressionJobs → mediaProtocol) and
               streams the settled file instead of false-flagging it
               missing. v3.1 covers the last observer: DTO building
               (library:list / updateDurations) waits out the swap through
               the same tracker and re-reads the record, and the Settings
               flow re-reads the library once the compress settles either
               way — the download-then-compress repro that used to strand a
               "file not found" row until restart is pinned by tests end to
               end.

DELETE         Row-menu delete → ConfirmDialog (or Settings row → in-dialog
               confirm) → api.library.remove → trash the file first (skipped
               if already missing) → remove row → cascade out of playlists →
               library/songsRemoved (scrubs the engine's order, history AND
               played maps — both paths) → renderer refetch.

ERRORS         Main wraps import/trash/ytdlp work in withErrorReport: pushes
               an AppError on the error channel AND rethrows so the invoke
               rejects. The renderer normalizes both through errorMessage()
               and the reducer collapses exact duplicates; distinct messages
               stack as toasts.

5. INVARIANTS WORTH KNOWING (the things reviews bled for)
--------------------------------------------------------------------------------
- ONE store instance set (library, playlists, settings, tags), constructed
  once in index.ts and shared by IPC, media protocol, and importer. Stores
  cache their JSON forever; two instances over one dir = stale reads +
  clobbered writes.
- SongDto.sizeBytes is null EXACTLY when exists is false — one measurement
  produces both fields, at all three producers (library IPC, ingest IPC,
  and the renderer's songMissing reducer case); since v2.1 the test mocks
  and harness enforce it on seeds too.
- In-flight compressions are tracked in main (compressionJobs); a media://
  request for a compressing song waits for the settle and reads the record
  fresh. The renderer-side guard (no compressing the cued song) holds the
  reverse direction. Since v3.1, DTO measurement (library:list /
  updateDurations) takes the same wait-then-re-read path, and the Settings
  compress flow re-reads the library on settle — a raced "missing" verdict
  can no longer outlive the moment it was wrong.
- The sidebar's order IS playlists.json's array order (v3.1): reordering
  crosses playlists:reorder as one whole-order payload, refused outright
  unless it names every playlist exactly once; create still appends; no
  drag while the sidebar filter narrows the list or a rename is open; OS
  file-drags are left alone — nothing takes a dropped file.
- Mouse clicks never park focus on a control (v3.1, useClickFocusReset):
  focus returns to the body after every pointer click on a button or
  slider, so the global shortcuts always work. Keyboard-activated clicks
  and everything menu-shaped are exempt — menu focus is programmatic and
  load-bearing.
- The app renamed to Audi0z (v3.1) but LIBRARY_DIR_NAME did not: the
  library folder stays ~/Music/my-music-library so no existing library is
  stranded. Only the packaged userData folder moved with the name (it held
  nothing but a re-downloadable yt-dlp copy).
- Shared-contract changes (src/shared/*, storeTypes) are additive-or-removal
  sweeps landing in ONE commit across api.ts, the preload, the mock and the
  handler — api.test.ts's structural equality plus the compiler enforce it
  (DESIGN.md records the rule; the old "frozen" claim is retired).
- The VIEW and the QUEUE are separate: browsing never pauses playback; only
  playing a song (or the TopNav play button) moves the queue, via
  queue/selected + startSongId (the id must be in the dispatched order —
  the engine trusts its callers on that).
- Ordering has ONE implementation: songsInView/sortSongs (viewSongs.ts) feed
  the list, the TopNav play button AND App's queue-resync memo, all with the
  same global SortMode — so a sorted view, the queue it hands over, and a
  live queue being re-sorted can never disagree. The sort is view-layer and
  session-only; stored order (library insertion, playlist manual) is never
  rewritten.
- Scrub silence is ELEMENT-local: seeking pauses/resumes the <audio> element
  directly and never dispatches, so playback.isPlaying (and the ⏸ glyph)
  stay honest through a drag, and a store-level pause always wins.
- The duration backfill yields to playback: no new probe starts while a song
  plays (the media:// handler's idle path is also await-free). The song
  playing has first claim on the disk — since v3 the code enforces what the
  comment always claimed.
- The Tags dialog is the only creator/renamer/deleter of tags; song rows
  and the add dialog only pick from the registry. Registry mutations
  cascade through the library in one persist — and a same-name rename must
  stay a no-op (the unguarded version deleted the tag from every song).
- The importer is the ONLY writer of new songs; ids and audio filenames
  derive from the same uuid.
- Custom error names don't survive IPC — message-text matching in
  renderer lib/errors.ts is the contract.
- The playback engine is pure; the <audio> element is driven exclusively by
  (currentId, playToken) — src changes only on id change, playToken bumps
  restart playback.
- All JSON writes are atomic (temp+fsync+rename); corrupt files quarantine
  to .bak and the app keeps running.
- One download at a time (BUSY latch); cancel must always release the latch
  (SIGKILL escalation guarantees the child dies).
- yt-dlp arg list: --print implies --quiet, so --progress must stay paired
  with it or the progress bar dies silently.
- Renderer code never imports Node builtins (enforced by the split
  tsconfig programs); renderer tests never import tmpLibrary.
- macOS packaging must produce SOME signature (ad-hoc via the afterPack
  hook) or arm64 refuses to launch; electron-builder's identity:'-' and
  publish defaults are both booby-trapped (see electron-builder.yml
  comments).
